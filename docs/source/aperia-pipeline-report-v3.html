Tech Stack

Every tool has a single, non-overlapping role. This stack covers the library (aperia-ds5) — consuming projects only need React, a framework, and Tailwind.

Theming approach: Consuming projects import aperia-ds5/base.css and override a small set of CSS custom properties by hand. The designer provides the values; the developer writes them into the project's theme file. No automated token pipeline.
03

Token Architecture

Tokens are hand-authored directly in base.css as CSS custom properties — no build step or generated files. The library ships this single file. Consuming projects import it and manually override only the variables that differ.

How the CSS cascade works

/* project globals.css */

@import "aperia-ds5/base.css";   /* library baseline + all default tokens */

@layer base {
  :root {
    /* hand-written overrides — developer reads Figma, writes these */
    --brand:  #E85D26;
    --radius: 0.375rem;
    /* everything else falls back to library default silently */
  }
}
Why manual is fine here: Brand tokens change infrequently — typically once at project setup and occasionally for rebrands. A 5-line :root override written by hand is faster to set up and easier to maintain than an automated export pipeline.

The library's default theme (not edited by projects)

/* aperia-ds5/styles/base.css — default tokens */
@layer base {
  :root {
    --background: oklch(1 0 0);
    --foreground: oklch(0.145 0 0);
    --primary:    var(--brand);
    --brand:      #002F67;   /* Aperia default — overridden per project */
    --radius:     0.625rem;
    /* ... all shadcn semantic tokens ... */
  }
}

@theme inline {
  --color-background: var(--background);
  --color-primary:    var(--primary);
  /* ... Tailwind bridges ... */
}

05

Library package.json

The dependency split differs slightly between the two distribution methods. The core rule: React in peerDependencies + devDependencies, never in dependencies alone. Build and DX tools (tw-animate-css, tsup, Storybook) in devDependencies — they are not needed at runtime by consumers.

Option A — Monorepo (workspace:*)

Consuming apps are in the same repo — the workspace manages React versions. peerDependencies are optional but good practice.

// packages/aperia-ds5/package.json
{
  "name": "aperia-ds5",
  "private": true,   // stays private, never published
  "dependencies": {
    // runtime — ships with the library
    "class-variance-authority": "^0.7.1",
    "clsx":           "^2.1.1",
    "lucide-react":   "^1.8.0",
    "next-themes":    "^0.4.6",
    "radix-ui":       "^1.4.3",
    "tailwind-merge": "^3.5.0"
  },
  "devDependencies": {
    // build + DX tools only — not shipped
    "react":              ">=18",
    "react-dom":          ">=18",
    "@figma/code-connect": "^1.4.3",
    "tw-animate-css":     "^1.4.0",   // Storybook preview only
    "tsup":               "^8.5.1",
    "typescript":         "^5.9.3"
  }
}

Option B — Published npm package

peerDependencies are required here — they tell npm "the consuming app must provide these." Without this, npm would install a second copy of React inside the library, breaking hooks.

// packages/aperia-ds5/package.json
{
  "name": "aperia-ds5",
  "private": false,  // publishable
  "peerDependencies": {
    // consuming app must provide these — NOT bundled
    "react":     ">=18",
    "react-dom": ">=18"
  },
  "dependencies": {
    // runtime — ships with the library
    "class-variance-authority": "^0.7.1",
    "clsx":           "^2.1.1",
    "lucide-react":   "^1.8.0",
    "next-themes":    "^0.4.6",
    "radix-ui":       "^1.4.3",
    "tailwind-merge": "^3.5.0"
  },
  "devDependencies": {
    // build + DX tools only — not shipped to consumers
    "react":              ">=18",
    "react-dom":          ">=18",
    "@figma/code-connect": "^1.4.3",
    "tw-animate-css":     "^1.4.0",   // Storybook preview only
    "tsup":               "^8.5.1",
    "typescript":         "^5.9.3"
  }
}

One import at the framework's entry point — whole app is styled.

4

Use components

import { Button, Card } from 'aperia-ds5'

Library update

npm update aperia-ds5
# globals.css theme is untouched — only library internals update

AI code generation

1

Designer shares Figma frame

Hands off a specific frame or component link to the developer.

2

Developer runs Claude with Figma MCP

Claude reads the Figma frame directly via the MCP connection.

3

Code Connect resolves components

The .figma.ts files tell Claude: "this Figma Button = <Button> from aperia-ds5." ShadcnDesign Agent Skills provide additional context.

4

Claude generates production code

Output uses correct aperia-ds5 imports, right prop names, and the project's active brand theme already applied.

Figma Kit

✓
ShadcnDesign
shadcn-endorsed kit with 2,000+ components, component-level Figma Variable linkage, and a Figma plugin that generates shadcn/ui component code from frame selections. Includes Agent Skills for Claude, Cursor, and Codex. Actively maintained.
Agent Skills vs Code Connect: ShadcnDesign's Agent Skills output code against stock shadcn/ui imports. Code Connect (.figma.ts files) additionally maps those components to aperia-ds5 specifically. Both are needed — Agent Skills for broad context, Code Connect for the correct package.
09

Design Decisions

Key choices made in this pipeline and the reasoning behind them.

Figma kit — ShadcnDesign

The shadcn-endorsed Figma kit. Chosen because it mirrors the shadcn/ui component model 1:1, ships with Agent Skills for Claude and Cursor, and has component-level Figma Variable linkage. This means Code Connect mappings stay accurate without custom maintenance.

Token approach — designer hands off, developer writes

No automated token export pipeline. The designer provides the values directly (brand color, radius, etc.) and the developer writes them as CSS custom property overrides in the project's theme file. Brand tokens change infrequently — typically once at project setup — so a 5-line :root block is faster and simpler to maintain than a sync pipeline.

Token ownership — library ships defaults, project overrides

The library (aperia-ds5) ships a complete default theme in base.css. Each consuming project imports it and only overrides what differs. This keeps project setup minimal while giving full control over brand identity.

Distribution — monorepo or published npm

Both models are supported. Use workspace:* when all consuming projects live in the same repo. Publish to npm (or GitHub Packages) when projects are in separate repos or maintained by different teams. The library's public API is identical in both cases.

Framework agnosticism

The library has no framework dependency — React is declared as a peer dependency only. Consuming projects bring their own React and framework (Next.js, Vite, Remix, etc.) without version conflicts.

Open questions

Version sync strategy between the Figma kit and the npm package is not yet defined. Workflow for net-new components beyond shadcn (custom Aperia-specific components) is also not yet established.
